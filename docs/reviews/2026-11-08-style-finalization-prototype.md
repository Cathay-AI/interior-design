日期：2026-11-08。對象：[產品設計簡報](../proposal/product-design/index.html)（21 頁）。本文是候選評估，不是選型結果；選型仍依 [架構 v0.2](../engineering/architecture.md)「尚未選定」的原則，用共同驗收案例比較。

## Prototype

路徑：[`docs/proposal/product-design/prototype/`](../proposal/product-design/prototype/index.html)（vanilla HTML／CSS／JS，無建置；只從 Google Fonts 載入 Manrope，離線時退回系統字體；不呼叫任何服務）。

本機開啟：`cd docs/proposal && python3 -m http.server 8765` → `http://localhost:8765/product-design/prototype/`。桌機左側有「這一步／系統學到／決策引擎視角／正式版技術與風險」註記；手機寬度改由右上角 `i` 打開。

### UX 修訂（2026-11-08）

依 design-taste-frontend 的 app screen 規則修訂；品牌色和宋體標題沿用主簡報。

- 看屋二選一的 A、B 兩張圖固定在同一個畫面（之前手機上 B 圖要捲動才看得到）
- 主要按鈕固定在畫面底部；左滑後的原因選項直接疊在卡片上
- 「上一步」會一併復原答案（看屋、滑卡、人格、鎖定、語音修改都適用）
- 上方進度列顯示目前關卡名稱與題數；亮亮那一列改成給提示和作答回饋，不再重複標題
- 等待時有骨架畫面或進度提示：模擬家人作答、重抽、3D 背景生成
- 鎖定標籤加上文字，第一次進入時會出現提示；3D 加上左右旋轉按鈕，可用方向鍵旋轉，桌機也可以按住空白鍵說話
- 移除背景漸層和靜止時的陰影，只保留亮亮與進度房子的光；emoji 換成 Phosphor 圖示；字級、間距、圓角都對齊級距

量測：lint 從 16 FAIL 降到 0；inspector 從 3 FAIL 降到 0，剩 3 個 WARN（品牌米白色、Songti 是系統字體所以偵測為未載入、開場畫面刻意留白）。

### UX 修訂 v3.1（2026-11-12）

依 redesign-existing-projects 的稽核，處理操作、狀態與無障礙問題（視覺層在 v2 已處理）。

- **錯誤**：畫面切換中的連點會被忽略（之前連點「開門」會跳過選路線，連點看屋會把答案記到還沒看到的那組圖）；重新產生畫面後，鍵盤焦點和捲動位置會還原；快速路線和參考圖路線在定案卡補兩題（收納、光線），兌現「跳過人格就補題」的說法
- **回饋**：提示訊息移到上方，可換行，不再蓋住主要按鈕；關卡進度只顯示這條路線有的關卡；重新打開時顯示「已接續上次的進度」並提供「從頭開始」；「點亮亮可開啟語音」只在前 3 個畫面出現；猜中結果改為逐題列出（換了什麼、我猜、你答）；下方還有內容時，按鈕列上緣加淡陰影
- **觸控與無障礙**：可點元素至少 44px；鎖定清單整列可點，圖上標籤只當滑鼠／觸控捷徑（不進 Tab 順序）；底部面板有標題標記、Tab 鎖在面板內、關閉後焦點回到開啟它的按鈕；打字輸入加上可見 label 和取消按鈕
- 另外修正：快速路線重新整理後，定案卡會被塞入預設人格；亮亮上一句回饋會被存檔、重開時又出現

驗證：上述每項都寫成自動檢查（16 項），在 390×844 與 1280×900 全部通過，三條完整路線無 JS 錯誤、無水平捲動。

### 可走進去的 3D 與主視覺（2026-11-12）

- **3D 提案改用 three.js r180**（[room3d.js](../proposal/product-design/prototype/room3d.js)），從 CDN 載入；載入中或失敗（例如離線）時，沿用原本的 CSS 3D 示意
  - 家具用免費授權模型：Poly Haven（CC0）的茶几、吊燈、植栽、收納櫃，以及 Khronos 範例庫的 GlamVelvetSofa（Eric Chadwick © Wayfair，CC BY 4.0）。出處見 [models/CREDITS.md](../proposal/product-design/prototype/models/CREDITS.md)，畫面下方也有標註
  - 模型以 gltf-transform 轉成 GLB、貼圖轉 WebP：首次載入約 1.2 MB，收納櫃另 1.2 MB，語音要求加收納時才載入
  - 地板、牆、地毯、窗簾、掛畫由程式產生，跟著元素清單換色；物件名稱就是元素清單的 key
- **操作**：拖曳環顧、點地板走過去、點家具顯示名稱並提示可用的語音指令；有三個預設視角（門口、坐在沙發、窗邊），可用方向鍵移動；觸控裝置可以轉手機看（陀螺儀，iOS 需授權）；瀏覽器支援 WebXR 時會出現「進入 VR」
- **元素清單抽成 [catalog.js](../proposal/product-design/prototype/catalog.js)**，prototype 和主視覺頁共用
- **主視覺**：[keyvisual.html](../proposal/product-design/prototype/keyvisual.html) 用同一個 3D 客廳拍出電影感靜態圖（黃昏光束、夜晚燈光、暗角、顆粒），再疊上品牌標題；輸出在 [key-visuals/](../proposal/product-design/key-visuals/README.md)，包含開場、簡報封面、分享卡和六種風格代表圖。沒有使用 AI 生圖
- **主視覺放進 prototype**（使用不含文字的版本，放在 `key-visuals/app/`，共約 670 KB）：
  - 開場畫面改用 3D 客廳夜景，按下「開門」時畫面會推近
  - 「先看預覽」和「選方向」改用六種風格代表圖
  - 人格卡和同住組合的「分享」會用 canvas 產生 1080×1350 的分享圖，可預覽、可儲存；圖上不含預算與照片

### 捲動與景深動效（2026-11-12）

依 gsap-framer-scroll-animation 與 premium-frontend-ui 的原則（電影感節奏、克制）處理。prototype 的捲動容器是手機框內的 `#screen`，而且畫面會整頁重畫，所以沒有用 GSAP，改用原生作法：sticky 釘住、自己算捲動進度、CSS scroll-driven animations。

- **開場「走進去」**：往下滑時，3D 鏡頭從門口走到沙發前，燈光由暗轉為吊燈亮起，再到黃昏斜陽；三段文案依序淡入。直接按「拿起鑰匙，開門」會在約 1 秒內自動走完。只在捲動時重畫一格，不跑持續迴圈。開場載好的 3D 場景，第 3D 關會沿用
- **換頁有景深**：前進時新畫面從後方推近，返回時反方向，子元素間隔 40ms 依序出現
- **捲動透視**：卡片、清單、選項進入視線時帶一點透視傾斜；風格圖和定案卡的房間圖有輕微視差。瀏覽器不支援 scroll-driven animations 時直接顯示，不影響操作
- **3D 導覽一圈**：鏡頭依序走過門口、坐在沙發、窗邊，再回到門口
- **減少動態效果**：開場改為靜態圖加上全部文案，其餘動效也一併關閉

### 電影章節式重新設計（2026-11-12）

問題：扁平等角插畫和擬真 3D 混在一起；每頁都是「標題、米色面板、按鈕、亮亮列」同一個樣板；關卡之間沒有敘事。改法：整個流程發生在同一個 3D 客廳裡。

- **常駐舞台**：three.js 客廳鋪滿整支手機，所有頁面都疊在它上面。每頁定義自己的鏡位、光線和要呈現的設計，換頁時鏡頭滑到下一個位置。面板會擋住畫面下半部，所以鏡頭取景中心往上移（`setViewOffset`），讓主角落在可見區域
- **扁平插畫全面換成 3D**：
  - 看屋二選一、滑卡：用同一個場景拍快照
  - 口味滑桿、只改牆色（改成色票）、猜中測試、試住白天／傍晚、定案卡：直接改背景的客廳
  - 鎖定：標籤貼在畫面裡的家具上
  - 3D 那一關：整個畫面就是可以走動的客廳，HUD（版本、視角、導覽）在上，麥克風和建議句子在下
- **章節過場**：進入新的一關時，顯示約 1.7 秒的「CHAPTER 0N」標題卡，鏡頭同時移動，點一下可以跳過
- **深色玻璃介面**：題目用襯線大字、字幕位置；選項是半透明玻璃；需要自帶圖片的頁面（看屋、人格、家人、商場、選方向）會把背景模糊、壓暗
- **亮亮**：不再常駐。只在有回饋時以泡泡出現在頂列下方；提示文字改給螢幕閱讀器讀；語音開關移到註記面板和資訊頁
- **後備方案**：WebGL 載入前或失敗時，舞台顯示預先拍好的風格圖，快照改用原本的程式插畫，流程不受影響
- 商場的單品沒有 3D 模型，保留線條示意圖，只換成玻璃版面

驗證：在 390×844 跑完完整、快速、預覽中途改走快速三條路線，以及 16 項 UX 檢查、開場 6 項、3D 5 項，全部通過，無 JS 錯誤、無水平捲動。1280×900 的結果另列於本次回報。

### 白色面板、排版重整與材質升級（2026-11-12）

- **白色面板**：內容放在中性的純白面板上，背後的 3D 客廳不再壓暗，所以介面配得起任何風格。元件不用框線，選取狀態改用填色；層次只靠淺灰色階。開場的電影鏡頭維持深色
- **排版重整**：選路線、口味、預覽、選方向、定案卡改成排版式的列：
  - 風格名稱用大字排出；說明寫成完整的句子
  - 「標籤—內容」的事實列取代膠囊標籤和小字標題
  - 口味的判讀改成文字（例如「偏冷調」），點一下就翻轉
- **10 種風格**：新增輕奢、韓系奶油、中古世紀、侘寂。每種風格有自己的沙發、茶几、吊燈、植栽與單椅：
  - 復古：切斯特菲爾德皮沙發配雕花茶几與提燈
  - 工業風：鐵件茶几配工業吊燈
  - 法式：雕花沙發、水晶燈與單椅
  - 輕奢：大理石茶几配黃銅吊燈
  - 侘寂：中式茶几配陶盆
- **實拍材質**：地板與特殊牆面改用 Poly Haven 的 CC0 PBR 材質（顏色、凹凸、粗糙度）。一般油漆牆使用灰泥的凹凸紋理再依牆色染色，地毯、窗簾與沙發布料各自疊上布料的凹凸紋理；牆面 UV 以公尺計算，貼圖在各面牆上的比例一致
- **檔案**：模型共約 15 MB、材質約 2.5 MB，依插槽在需要時才載入。單一風格約 2–4 MB
- **元素清單**：新增大理石、柚木拼花、原木地板、清水模、藝術灰泥、奶油白、橄欖綠、香檳灰、奶油毛圈、香檳絨、切斯特皮、雕花布面、雕花皮革、復古提燈、幾何花紋等選項，語音指令也一併支援。「深色磁磚」改為「水泥粉光」
- **主視覺**：重拍 10 種風格的代表圖、App 用的無文字版，以及開場、封面、分享卡。文字改放在實心白色面板上，拿掉編號、小標與文字陰影
- 設計 lint（design-taste-frontend）對整個 prototype 資料夾為 0 項

### 功能補完與剩餘頁面重排（2026-11-12）

把還沒換過排版語言的四頁（參考圖、家人、商場、試住）改成同一套字體排印式版面，並補完先前承諾過但沒做完的功能。

- **商場重做**：四家店賣的就是元素清單裡的選項（沙發、燈具、窗簾、地毯），不再有另一份商品目錄。單品特寫由同一個 3D 場景即時拍攝——把該選項套進你目前口味的客廳，拍一張特寫；模型還在載入時先用線圖，載好自動補拍
- **收藏變成真的功能**：選方向時，收藏的單品若和該風格相容、又不和房裡其他東西衝突，會直接放進佈置；不搭的會說「先留在收藏」，不會默默消失
- **定案卡可編輯**：「不要」和「準則」每一條都是可移除的標籤，「＋」開選單（建議清單＋自由輸入）。增刪會存檔、可還原（上一步）
- **打字入口**：3D 關的建議句子列加上「用打字」，支援語音的瀏覽器也能用打字改
- **選路線頁**不再承諾「隨時可以換路線」（功能沒做，文案改掉）
- **重構**：刪掉獨立的 SHOPS 商品目錄與 42 條死 CSS；抽出 openTyped／openPicker 共用
- 另外採納同儕審查的兩點：收藏套用前跑衝突表；被跳過的收藏要向使用者說明原因

### 效能與場景寫實（2026-11-12）

原則：寫實靠便宜的視覺線索，效能靠「只在需要時畫」。

- **自適應畫質**：只有 3D 那一關跑連續繪製，其他畫面每次變化只畫一格。連續繪製時監測滾動平均幀時間，幀時超過 2.5× 螢幕更新預算先把解析度降到 1.4 倍、再降到 1 倍並關閉陰影；穩定低於 1.1× 預算再逐階恢復（降階間隔 2.5 秒、升階 6 秒，暖機 60 格後才開始判斷；預算由裝置自身的更新率自校準）
- **窗外有世界**：窗景從純漸層換成程式繪製的天際線＋前景綠意；入夜後遠處大樓亮起點點窗燈。一張 128×256 的 canvas 貼圖，零額外下載
- **牆角環境陰影**：牆腳、天花板線與牆角放了 8 條漸層暗帶，模擬 AO 的視覺線索，成本幾乎為零（真 AO 手機跑不動）
- **傍晚燈罩會發光**：吊燈點亮時燈罩材質同步給 emissive，不再只有光照亮房間、燈本身卻是暗的；換燈具模型也會跟上
- **主題牆**：裝飾度 ≥2 的風格（復古、法式、輕奢、中古），沙發牆用同色深一階的漆，貼圖牆則壓暗一階——台灣常見的電視牆／沙發牆作法，也讓 10 種風格的同一間房看起來更不一樣
- **圓形地毯**：地毯有長方形與圓形兩種形狀（白色長毛為圓形），北歐、輕奢的預設房間因此和其他風格的輪廓不同

### 每種風格有自己的佈置（2026-11-12）

再加 11 個 Poly Haven CC0 模型（共約 2.4 MB），場景多三個擺位，10 種風格的房間不再只是換沙發和顏色：

- **新擺位**：邊櫃（靠左牆）、屏風（後角）、桌上擺飾（茶几上，與桌上植栽分開放）
- **各風格的配置**：無印＝展示層架＋白瓷瓶；北歐＝淺色開放層架；復古＝復古五斗櫃＋青花瓶；工業＝鐵件層架；簡約＝什麼都不加（留白就是它的佈置）；法式＝古典瓶；輕奢＝皮革腳凳＋黃銅瓶；韓系＝奶油色塗裝櫃；中古＝五斗櫃＋黃銅瓶；侘寂＝木框布墊沙發（新沙發選項）＋中式屏風＋陶瓶
- 元素清單新增「木框布墊」沙發選項（侘寂預設），語音可叫；佈置模型是風格陳設，不進報價
- fit 的 maxH／maxW 改為取最小縮放，邊櫃與提燈加上尺寸上限，避免壓到前景

驗證：完整、快速、預覽改道三條路線與 18 項 UX 檢查在 390×844 與 1280×900 全部通過，開場 6 項、3D 5 項、人格測驗流程無 JS 錯誤。效能量了快慢兩端的實際硬體路徑：

| 環境 | 結果 |
| --- | --- |
| Apple Silicon 真 GPU（手機視窗 390×844、dpr 3、量 36 秒） | 穩定 60fps、3D 幀時 17ms、畫質維持「高」、heap 峰值約 30MB（載入時）後回落 21MB——快的裝置不降階 |

| **WebKit（iOS Safari 引擎）**，Playwright WebKit 27.2＋iPhone 15 模擬 | 60fps、17ms、滿畫質、console 零錯誤——iOS 的渲染引擎路徑成立 |

**手機實測路徑已備好**：加上 `?debug=1` 會在左下顯示 fps、畫質階、3D 幀時與 heap。手機與電腦同一個 Wi-Fi 時，開 `http://<電腦IP>:8765/product-design/prototype/?debug=1` 即可直接讀數（`cd docs/proposal && python3 -m http.server 8765`）。

### 看屋改成真樣板房（2026-11-13）

二選一與滑卡的每個選項，從「同一間房換顏色」改成完整的風格樣板房：

- 每張候選圖先把偏好向量對應到最近的風格（含該風格的家具、邊櫃、屏風、掛畫、植栽），再用向量在風格內挑相容變體（地板、沙發、窗簾……），並在三個鏡位間輪替——同風格的兩間房也長得不一樣，跨風格的對比是真的家具差異
- 家具還在載入時先出圖、載好自動重拍（沿用商場的 whenModel 機制）
- 修正：絨布 sheen 全強度在掠射角像金屬，壓到 0.35；布料凹凸／粗糙貼圖開場預載（半載入的粗糙貼圖取樣為 0，沙發會變鏡面）；redraw 的 TDZ
- 引擎學習邏輯不變：仍以同一組三維向量作答
- **選得出來的配對**（使用者回饋「都很像、選不出喜歡的」後補強）：
  - 二選一強制跨風格：A、B 一定是兩種不同風格的房子；滑卡一副牌裡不重複風格
  - 打光偏向黃昏斜陽（最討喜的光），快照加輕微飽和／對比調色
  - 修正快照殘影：快照改嚴格模式——目標家具未就位就先隱藏、不拍到上一間房的家具；已就位的模型同步換上（Promise 晚一拍會拍到舊沙發）；whenModel 等模型真正裝進場景才算數
  - 64 間候選房對風格的分布實算過：每種風格都有
- **風格增至 14 種**（使用者回饋「風格還是不夠多元」後擴充）：新增台式老宅（水磨石、木百葉、屏風、老木家具）、波希米亞（陶土、花紋織品、植栽）、地中海（白牆、靛藍布沙發、條紋地毯）、沉穩酒店（炭黑牆、黃銅、大理石）。全部用既有模型與程式材質組成，零新下載；元素清單新增靛藍、炭黑牆色、靛藍布沙發、靛藍條紋與焦糖編織地毯（地毯紋理新增條紋與編織兩種程式畫法），語音同步支援；日光北歐的向量微調後，64 間候選房涵蓋全部 14 種風格

降階門檻改為**自校準**：以暖機期第 26–55 格的**中位數**估計螢幕更新間隔（WebKit 驗證抓到 min 估計會被單一異常 dt 污染、卡死在低畫質——跨引擎測試的實際收穫），超過 2.5× 預算降階、低於 1.1× 回升——60Hz／120Hz 裝置同一套邏輯，沒有需要實機校準的常數。三個體制驗證：真 GPU 與 WebKit 滿畫質不降、軟體 GPU 於 28 秒降到 1×。

**後續里程碑的 QA 項（自 v2 起即列）**：

- 實體手機的發熱。幀率、引擎（WebKit）、CPU／GPU 弱裝置、傳輸量皆已依上表驗證；發熱是唯一無法遠端量測的項目，拿手機開 `?debug=1` 的區網頁即可順手確認

- 實機陀螺儀
- VR 頭顯（手邊沒有裝置；iOS Safari 不支援 WebXR VR）

### AI 版流程（2026-11-18）

目標是讓流程更 AI first：由模型的理解推動流程，而不是讓使用者先選路線、再走固定關卡。先用模擬確認哪些做法真的有效，再決定要做什麼。

**模擬方法**：沿用 prototype 的偏好模型、64 間候選房與 14 種風格向量，模擬一致、普通、不一致三種使用者（作答時的隨機程度不同），每種 300–600 人。數字只適合在同一組模擬內比較；真人資料要等使用者測試。

| 做法 | 結果 | 決定 |
|---|---|---|
| 不確定度低於門檻就停題 | 不確定度只取決於問了哪些題，不取決於答案；三種使用者在第 6 題的數值幾乎相同，等於變相固定題數 | 不採用 |
| 「猜測連續不變就停」（最少 3、最多 9 題） | 平均 5.8 題，準確度與固定 6 題相同（例如一致型使用者第一名猜中 0.79 對 0.80） | 不採用 |
| 用「模型猜中作答的機率」判斷使用者是否一致 | 因為出題時刻意挑模型最沒把握的配對，三種使用者的數值都在 0.5 左右，無法區分 | 不採用 |
| 「先猜再驗」：第 4 題起出模型有把握的配對，連猜中兩次就停 | 平均少不到 1 題，但第一名猜中率下降約 6 個百分點（驗證題的資訊量較少） | 不採用 |
| 前兩名風格的分數差 | 差距 ≥ 0.15 時第一名猜中 64–69%，< 0.15 時只有 35–54%，這是唯一和答案有關的訊號 | 用來決定「顯示猜測」或「還在兩者之間」 |

結論：在 3 個維度、14 種風格的模型下，固定 6 題已接近上限，自適應停題只會「看起來」比較聰明，所以沒有做。「由 AI 決定跳過哪些關卡」需要同一種訊號，也一起擱置。要真的能依人調整，得先擴充模型（更多維度，或用真實資料建立先驗）。

**實際做的（AI 版，預設）**：

- **作答時顯示目前猜測**：看屋與滑卡的題目下方有一列「你的家目前像」，附上第一名風格的縮圖。前兩名分數差 < 0.15 時誠實顯示「還在 X 和 Y 之間」
- **每次作答說明改變的原因**：亮亮的回饋改成例如「猜測從『無印日式』換成『波希米亞』：你選了比較暖調的那間」，原因取自兩間房差最多的維度
- **拿掉開場的路線選單**：開門後直接看屋，「完整闖關或直接佈置」改在預覽畫面決定，也就是使用者先看到 AI 的結果再選；「我已經有參考圖」改成開場頁的連結
- **AI 版／固定版切換**：註記欄（手機在 `i` 面板）可切換，切換後從頭開始，方便並列比較；固定版保留原本的三條路線

驗證：Chrome（軟體 WebGL）與 WebKit 2391 在 390×844 跑過 AI 版流程，包括不經路線選單直接看屋、兩張房間圖都在操作列上方、六題的猜測與原因文字、上一步復原答案、預覽頁的兩個選項、參考圖連結，以及切回固定版時路線選單會出現。兩個引擎都沒有錯誤。沒有 GPU 的 headless Chrome 無法建立 WebGL，這是測試環境限制，頁面會改用預拍的靜態圖。

## 建議技術（候選）

| 層 | 建議 | 理由 |
|---|---|---|
| 前端 | 手機優先 Web（PWA）、React＋TypeScript＋Vite；流程用狀態機（XState 或 reducer） | 團隊熟悉；關卡、路線、跳過、存檔本質上是狀態機 |
| 動效／2.5D | CSS transitions、scroll-snap、SVG／Lottie | 商場與闖關都不需要 WebGL |
| 3D | GLB（Draco／meshopt 壓縮）＋ three.js / React Three Fiber；只檢視可用 `<model-viewer>` | 物件要命名（`sofa`、`wall_tv`），語音工具呼叫才改得到 |
| 後端 | FastAPI＋PostgreSQL（圖片屬性、選擇紀錄、版本）＋物件儲存＋背景任務佇列 | 生成類修改一律背景任務 |
| 決策引擎 | 先上基準模型（prototype 的 logit 約 60 行，可在前端或後端跑）；JEV 放在可替換介面後面 | JEV 仍在早期存取、託管在美國、保留期限未明 |
| 圖庫 | 60–100 張授權圖，人工標屬性；佈置關卡用**分層素材**（地板／牆／沙發各一層） | 鎖定與重抽可以即時、一致、零生成成本 |
| 生成 | 只在定案後與 3D 階段使用；局部修改用 inpainting／遮罩，背景執行 | 見下方可行性 |
| 語音 | 階段 1：按住說話 → 伺服器端 STT → LLM tool call（場景 schema）→ 亮亮固定台詞預錄 | Web Speech API 只適合 prototype |
| 分享卡 | 伺服器端產生 OG 圖（Satori／Canvas），不帶預算與照片 | — |
| 家人共測 | 簽章邀請連結＋免註冊臨時 session；互看由伺服器控管 | 不靠前端隱藏 |
| 量測 | 漏斗事件（每關完成、跳過、家人完成、猜中率） | 對應簡報的 6 個驗證問題 |

## 可行性低（建議改設計或延後）

| 項目 | 問題 | 建議 |
|---|---|---|
| **在 AI 生成圖上鎖定元素、其他重抽**（第 5 關） | 純文字生圖無法保證「只換沙發、其他不變」；inpainting 每輪數秒到數十秒，又有成本 | 第 5 關改用分層素材即時合成（prototype 的作法），生成只用在最後一張 |
| **連續對話、可打斷** | 手機瀏覽器的回音消除、音訊路由（iOS Safari 尤其明顯）不穩 | 維持簡報的階段 3，先做按住說話 |
| **語音移動家具** | 沒有房間尺寸就無法做碰撞與通道檢查 | 沒有尺寸時回「做不到，需要尺寸」（prototype 已示範） |
| **自由走動的 3D 商場** | 資產與手機效能成本高，又只是用來萃取喜好 | 不做；2.5D 足夠 |
| **用自家照片換風格並保留結構**（試住上傳） | 結構保持與尺寸可信度不足，容易被當成「真的會長這樣」 | 首版不承諾；只當參考 |
| **3D 階段的粗略報價** | 沒有坪數和單價表就只能猜，違反「不用猜的數字」 | 坪數未知時顯示「待確認」或明確寫出假設（prototype 已改為「假設客廳 8 坪」） |

待驗證（不是做不到，但沒實測前不該承諾）：台灣口音與中英夾雜的 STT、家人實際完成率、圖庫授權成本、JEV 是否贏過基準模型、手機同時跑 3D 與語音的效能。

## 設計建議

做 prototype 時遇到、值得在下一版調整的地方：

1. **完整路線太長才看到成果。** 完整闖關約 16 個畫面，加上正式版的 12 題人格，估計要 12–15 分鐘才看到 3D，但 MVP 的核心價值（3D＋報價）放在最後。建議：看屋結束就給一張「你的家可能長這樣」預覽，並考慮預設推薦快速路線、完整闖關改為選修。
2. **家人共測不能卡住流程。** 家人是非同步作答，prototype 只能用「模擬」按鈕。正式版應該先往下走，家人完成時再通知，然後合併進定案卡。
3. **商場和看屋、佈置重疊。** 三者都在收集元素層級的喜好。建議把商場併入第 5 關變成「換單品」，或先用 A/B 驗證（簡報驗證題 5）再決定要不要做。
4. **猜中測試的題目要在已選方向之內。** 定案後再拿完全不同風格的留出圖來猜，對使用者意義不大，而且 5 題統計上不可靠。建議改用同方向的變體，並且當作軟提示，不要硬性退回第 5 關（prototype 猜中少於 3 張就會建議退回；自動測試一律答「喜歡」時只猜中 2 張，就觸發了退回建議）。
5. **統一元素清單。** 鎖定的元素、定案卡欄位、3D 物件名稱、報價項目，應該共用同一份 schema（地板、牆、沙發、窗簾、燈具、地毯…）。這會是工程上最省事的決定。
6. **偏好維度要少。** 看屋約 10–15 次比較，只能分辨少數幾個維度。prototype 用 3 維就收斂得很明顯，正式版建議 6 維以內，或用跨使用者的先驗（簡報的「階層模型」）。
7. **重抽要有搭配約束。** 純隨機重抽會出現不協調的組合（例如陶土牆配墨綠絨沙發）。重抽時要限制在同一風格的相容範圍內。
8. **亮亮的狀態只靠光線表達不夠明顯。** 靜音時需要清楚的圖示（prototype 有加）。瀏覽器規定自動播放必須先有使用者操作，所以語音預設關閉、由使用者點開，本來就是必要的。
9. **無障礙。** 每個手勢都要有對應按鈕：滑卡已有；3D 拖曳還缺左右旋轉按鈕；語音一定要能改成點選或打字。
