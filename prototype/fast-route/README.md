# 快速找風格原型（fast-route）

目標：讓人在一分鐘內看到喜歡的風格變成 3D；補上自己家的條件後，3D、估價、施工圖和法規評估都跟著貼近他家。四個畫面，唯一的表單是選填的。

| # | 畫面 | 做什麼 |
|---|------|--------|
| 1 | 滑卡 | 一次一張 Pinterest 靈感圖，右滑喜歡、左滑跳過（拖曳、✕／♥ 按鈕、方向鍵都行）。可撤回上一張；喜歡時可選填「喜歡它的什麼」（採光、配色、材質…）。共 18 張、每種風格 3 張；隨時可以「跳過選風格」 |
| 2 | 我家的條件 | 選填。開頭顯示滑卡結果並可改選任一風格；按麥克風用說的或打一句話，聽得出來的欄位自動填好；也可手填坪數、長寬、天花板高、屋況、樓層與隔間。另可附參考圖（平面圖、機電圖、照片）留給專業團隊，目前不會被判讀、不影響結果 |
| 3 | 3D 示意 | 依選定風格與填的尺寸生成即時 3D 房間：拖曳旋轉、A／B／C 視角、換風格、改細節。開不了 3D 的裝置改顯示 2D 示意圖，並收起沒有作用的視角按鈕 |
| 4 | 估價與施工圖初稿 | 逐項估價（標示「範例估算／初步估算，非正式報價」與假設）；六張施工圖初稿：沒填長寬時是可放大的範例，填了才是你家的並可解鎖；三階段說明；法規與施工條件評估 |

RWD：820px 以下單欄、主要按鈕貼底。

## 設計師要看得見

第一眼要看得出「這個產品會幫我設計我家」，不是風格測驗。做法是保留點選操作，但每一步都有設計師在回應（不是聊天機器人）：

- **開場**：一句承諾「滑幾張圖，我幫你設計你家」、一張成果預覽（3D 加預估金額）、設計師先問「想先弄哪裡？」。選完空間才開始滑卡，只多一次點擊。
- **步驟名稱以你家為主詞**：選喜歡的風格 → 告訴我你家 → 看你家的設計 → 知道要花多少。
- **滑卡時回話**：「收到，你家客廳會偏暖木色…」；抓到方向後邀請「要看看我幫你配的樣子嗎？」。
- **第 2 步由它追問**：一次只問最有用、還沒回答的那一項，並說為什麼問。
- **3D 出來時解釋配置**：走道留幾公分、櫃子為什麼放那面牆、哪些家具因為空間不夠沒放。數字來自真的配置資料。
- **改設計可以用說的**，改完回報對錢和法規的影響：「好，地毯拿掉。預估少約 1 萬；不用再處理防焰地毯。」聽不懂的會照實說還不會改。

這些話都在 `lib/voice.js`，用現有的分數、配置、估價和法規資料以模板組出來，**沒有接語言模型**，所以聽得懂的修改只有畫面上那四種和六種風格。要做到自由對話，需要接上模型（有成本與延遲），先用這一版驗證屋主是否買單。

## 體驗重做：依設計稿「實作優化＋整戶平面圖」

設計稿在 Claude 的設計畫布（Interior Design Agent 原型，頁面「實作優化＋整戶平面圖」）。這一版照它做，`lib/` 的估價、法規、配置、解析邏輯不動。PR 掛 `hold` 標籤，由 Victor 用預覽網址看過再合併。

**流程：你家 → 風格 → 設計 → 花費**

1. **你家**：開場丟平面圖就開始；還沒有平面圖可以先挑一個空間（客廳、臥室），填長寬。
   - 丟了平面圖會進「你家有這些房間，對嗎？」：一份三房兩廳的房間清單，可以取消勾選、改名稱與尺寸、加一間、刪除。
   - **會讀平面圖**：上傳的圖片或 PDF 送到 `api/read-plan.js`（Vercel 函式），由模型讀出每間房間的名稱與長寬（`lib/plan.js` 整理與驗證）。圖上沒直接標的尺寸標「請確認」。金鑰放在 Vercel 環境變數，不進瀏覽器：設 `OPENAI_API_KEY` 用 OpenAI（預設 `gpt-5.5`，可用 `OPENAI_MODEL` 換），沒設而有 `ANTHROPIC_API_KEY` 就用 Claude；沒設金鑰或讀不出來時退回三房兩廳範本，並在畫面上說原因。檔案不留存。
2. **風格**：滑卡；整戶時舞台放示意平面圖，風格整個家一起套用。
3. **設計**：一間一間看。舞台上方是房間列，右上是小平面圖，點了換房間；每間房各自記得改過的細節。換風格預設整個家一起換，取消勾選「整個家一起換」就只換這一間。貼底的動作列是「下一間」和「看整戶要花多少」。
4. **花費**：整戶合計，可以依房間或依工項看；取消勾選就先不做那一間，合計馬上更新。

**每一種空間都做得出設計**：客廳、臥室、餐廳、書房、廚房、衛浴各有自己的家具配置（`lib/layout.js`）、3D、六張圖面和估價工項；主臥、次臥用臥室的配置，認不出名字的房間（儲藏室、多功能室…）用書房的配置。不限制空間，畫面上沒有「還沒開放」。
   - 餐廳：餐桌配四張椅子、餐櫃、窗下備餐櫃。書房：書桌、工作椅、書櫃，夠大再放閱讀椅。
   - 廚房：一字型流理台（水槽、爐具）、吊櫃、冰箱；估價有廚具、給排水與瓦斯，沒有窗簾與家具。
   - 衛浴：洗手台浴櫃、馬桶、淋浴間；估價有衛浴設備、防水與給排水、壁磚。
   - 新加的四種空間，家具是程式建的簡單形體，沒有客廳那種掃描模型；地板和牆面的 3D 材質仍沿用風格的木地板與塗料（估價是照磁磚算的）。

**示意平面圖**（`lib/home.js` 的 `planSVG`）是依房間面積排出來的方塊，只表示有哪些房間和大概的大小，不是實際格局。

**版面與視覺**

- 左邊是滿版舞台（同一個 3D canvas 全程不卸載，背景透明、直接透出舞台底色），右欄固定 520px：上面是可捲的內容，下面是貼底的動作列。手機是舞台 310 高，右欄是往上蓋的圓角面板。
- 舞台上：左下尺寸卡、右下深色金額卡（變動時滾動）、開場的六個風格色票、設計頁的視角切換。
- 色彩是暖色紙面；陶土橘只給每頁唯一的主要按鈕，燈光黃只給進度「已完成」與亮亮。
- 字體：標題與金額 Noto Serif TC 900，其餘 Noto Sans TC。
- 圓角三級：膠囊（按鈕、選項、輸入）／16–20（卡片）／24（滑卡、手機面板）。卡片用底色分層，不用外框。
- 進度是有名字的四步；亮亮的話放在對話泡泡裡，一次一句。

**和設計稿不一樣的地方**

- 設計稿寫「我讀到三房兩廳」。實作會讀圖：讀成功顯示「我從平面圖讀到 N 間」，讀不成才給範本並說明原因。讀圖的準確度還沒用真實平面圖校驗過。
- 設計稿的整戶平面圖是一張畫好的三房兩廳。實作改成依房間清單排出來的示意方塊，這樣改了房間它會跟著變。
- 設計稿裡餐廳、廚房、衛浴的金額是空白的 `[ ]`；實作每一間都算得出金額並計入整戶合計。
- 整戶施工圖的價格在設計稿是 `[價格待定]`，實作照樣顯示「價格待定」。
- 沒有平面圖的備用流程，設計稿是先風格再你家；實作統一成你家 → 風格，少一套順序。

## 基本資料完整度（原「掌握度」）：給得越多，越貼近你家

畫面上叫「基本資料完整度」，因為填滿也只代表基本資料齊了：門窗、柱位、既有水電仍要現場確認，畫面上有註明。


`lib/context.js` 的 `contextScore` 把屋主補的條件換成 0–100% 的掌握度：長寬 40%（只給坪數 25%）、天花板高 15%、屋況 15%、樓層與隔間 20%、所在樓層與撒水頭 10%。只計「現在真的會改變結果」的條件；上傳的參考圖還不會被判讀，所以不計分。它會影響四件事：

- **估價**：`tighten` 讓每個工項的區間以中點為準收窄，掌握度滿分時寬度減半。
- **施工圖**：依實際長寬高重新配置（見下），否則依坪數換算的尺寸。
- **3D 房間**：`lib/layout.js` 的 `roomSize` 決定房間大小，客戶家多大就畫多大（百坪也照畫；只有小於 2 公尺放不下沙發、或大於 60 公尺時才取最接近的值並在畫面說明），`roomLayout` 讓家具靠著所屬的牆重新擺放：家具本身不放大，小房間沙發變兩人座、放不下的單椅、茶几、邊櫃、盆栽會自動拿掉。
- **法規與施工條件評估**：依樓層、所在樓層、撒水頭與隔間判斷；附了參考圖的項目從「待補資料」變成「待判讀」，但不會變成「已檢查」。

語音用瀏覽器內建的語音辨識（Chrome、Safari 支援；不支援時改打字），`lib/intake.js` 的 `parseHome` 會處理「八坪」「五米六」「280 公分」這類口語。

目前的限制：上傳的檔案只留在瀏覽器（`lib/docs.js` 只做分類與檢查），不會上傳也不會判讀內容；3D 只跟著長寬高改變大小，隔間、門窗位置仍是固定的示意格局。

## 估價：看設計，不問預算

`lib/estimate.js` 的 `designEstimate(cond, look)` 依這個設計實際用到的東西列出工項：地坪（木地板或礦物塗料）、牆面、收納櫃（木皮或烤漆）、燈具電工、窗簾、家具軟裝（布、絨、皮），中古屋與老屋再加基礎工程。在 3D 頁改設計，金額會跟著變。沒說坪數就用預設 8 坪並標示「預設」，在估價頁可以直接調。

單價是台灣參考行情的量級，尚未以實際單價表校正；用來看量級，不是報價。

## 施工圖：AI 初稿 → 專業團隊確認 → 施工圖定稿

目標是交付可施工的圖，由專業設計與施工團隊把關；這個原型目前只做到第 1 階段，介面上把三個階段與責任講清楚，還沒確定的部分標示為「確認中」，不寫成已經具備。

| 階段 | 誰負責 | 現況 |
|---|---|---|
| 1 AI 初稿 | 使用者提供長寬高、屋況、樓層；系統自動配置 | 已實作 |
| 2 專業團隊確認 | 設計與施工團隊：現場丈量、門窗柱位、既有機電、法規 | 流程確認中（預約方式、負責人、費用、時程未定） |
| 3 施工圖定稿 | 通過確認後才稱為可施工的圖 | 出圖標準確認中 |

`lib/drawings.js` 用和 3D 同一份配置（`roomSize` → `roomLayout`）產生六張 SVG：平面配置、天花板燈具、插座與弱電、收納櫃立面、地坪計畫、估價明細表。

- **跟著尺寸重新配置**：牆、窗、櫃、家具、嵌燈格點（約每 2.2 公尺一盞）、插座位置都依實際尺寸；小空間會少掉放不下的家具。
- **標準比例**：以 A3 橫式為準，自動選放得下的最大標準比例（1:20、1:30、1:50、1:100…）。
- **每張圖標示**「AI 初稿・需現場丈量，經專業團隊確認後才是可施工的圖」。
- **範例與你家的分開**：沒有手動填的長寬時是「範例」，可以直接放大看、不能下載、不賣，並列出還缺什麼；填了長寬才是「你家尺寸的初稿」，模糊、可解鎖、解鎖後可下載。上傳平面圖不算（`aboutThisHome`），因為還不會被判讀。
- **解鎖說明**寫明買到的是第 1 階段的 AI 初稿，專業確認不包含在內。

模糊是 CSS 效果、付款為模擬，原型階段沒有做圖檔保護。出圖標準確定後，圖框、圖例、線型與必備圖說套進 `lib/drawings.js`。

**待確認（產品決策）**：哪些資訊由使用者提供、誰負責丈量與審核、什麼條件下才能稱為可施工圖、使用者何時接觸到專業團隊、第 2 階段是否另外收費。

## 法規與施工條件評估

定位：**先知道這個設計在你家能不能做、要花多少、要辦什麼，再去找設計師。**

- **在 3D 頁、金額旁邊。** 一行結論，例如「這個設計需申請室內裝修許可・3 項要注意・再回答 2 題就能判斷完」，點開看細節。估價頁有同一份完整清單。
- **跟設計連動。** 只列這個設計真的有的東西：拿掉地毯，「防焰地毯」那一項就消失；臥室寫的是衣櫃、客廳寫的是高櫃。
- **差一個答案就當場問。** 「天花板有沒有撒水頭」「你家在第幾樓」可以直接在那一項底下回答，不用回上一頁；回答後「待補資料」變成明確結論，也計入掌握度。
- **圖上有標。** 立面圖標出撒水頭淨空線（迴水板下方 450、水平 300），天花板圖註明偵測器與撒水頭位置待現場標註。
- **每一項都有條文、修正日期、查證日期、確定程度**，條文連到全國法規資料庫。

`lib/rules.js` 的判斷（`LAWS` 是條文清單，`CHECKED` 是查證日期）：

| 項目 | 判斷 | 依據 |
|---|---|---|
| 室內裝修許可 | 六層以上集合住宅要申請（住宅可走簡易程序）；五層以下在增設廁所浴室或動隔間時要申請；透天獨棟一般不用 | 建築法第 77-2 條、建築物室內裝修管理辦法第 3、33 條 |
| 裝修材料耐燃等級 | **你家在十一層以上**：居室天花板與牆面耐燃二級以上；未達十一層的住宅居室沒有列等級 | 建築技術規則建築設計施工編第 88 條 |
| 防焰窗簾／防焰地毯 | 建物地面樓層達十一層以上要用附防焰標示的產品；設計裡沒有地毯就不列地毯 | 消防法第 11 條 |
| 撒水頭淨空 | 有撒水頭：迴水板下方 45 公分、水平 30 公分內淨空，櫃體與新天花板要讓開 | 各類場所消防安全設備設置標準第 17、47 條 |
| 火警偵測器／住宅用火災警報器 | 十一層以上建築是偵測器，其餘住宅是住宅用火災警報器；天花板重做都要留著 | 設置標準第 19 條、消防法第 6 條 |
| 避難與防火區劃 | 沒動隔間：說明這個設計沒有動到；會動隔間：待專業判讀 | 建築法第 77-2 條、公寓大廈管理條例第 16 條 |

狀態有六種：已檢查、衝突、待補資料、待判讀、需辦理、不適用。不知道就是「待補資料」，不猜；法規類項目不會被標成「已檢查」。

**條文核對的範圍。** 上表的條號與門檻（十一層、十六層、45／30 公分、1.2 公尺）已在 2026-11-13 對照全國法規資料庫的條文原文。兩件事**沒有**核對：一是「六層以上集合住宅屬供公眾使用建築物」「五層以下增設廁所浴室或兩間以上居室」出自內政部解釋令，資料庫裡沒有原文，畫面上標為「依內政部解釋令」；二是各縣市的自治規定與個案例外。這仍然是提醒、不是合格判定，適用與否由專業人員確認，修法後要重新核對並更新 `LAWS` 與 `CHECKED`。

## 進度、下載與隱私

- **進度存在瀏覽器**（`lib/persist.js`，localStorage）：重新整理不會從頭來；「重新開始」會清掉。上傳的檔案不存，還原後會提醒重新附上。沒有帳號。
- **分享連結**：3D 頁與估價頁的「複製分享連結」把風格、修改與條件編進網址（`toShare`／`fromShare`，不需要伺服器）；對方打開直接看到同一個設計與估價。不含上傳的檔案與解鎖狀態，內容經白名單檢查。
- **解鎖後可下載**：每張圖可在放大檢視時下載 SVG（檔名如 `A-01-floor-plan.svg`）。
- **空間範圍**：第 2 步風格選項下面有一排「客廳／臥室／廚房／衛浴／全室」，預設客廳、不選也能繼續；目前做了客廳與臥室，其餘標「之後」。一句話講到「主臥」會自動切到臥室。臥室有自己的家具配置（床、床頭櫃、衣櫃、窗下斗櫃、單椅）、3D、六張圖和估價工項（衣櫃、遮光簾、床組）。滑卡的圖目前都是客廳，只用來抓風格，畫面上有說明。
- **輸入不卡人**：一句話按 Enter 或「送出」就解析（Shift+Enter 換行，選字中的 Enter 不算）；尺寸有合理範圍（長寬 2–60 公尺、高 2–12 公尺、坪數 1–500、樓層 1–120），填錯的值留在欄位上、旁邊說明原因、不拿去算，也不會前進；游標還在欄位裡時按「生成 3D」一次就會前進。
- **改細節是開關**：按一次套用（有選中樣式）、再按一次取消，另有「復原上一步」。估價可以取消「家具軟裝」。解鎖後每張圖可下載 SVG，或用瀏覽器列印存成 A3 的 PDF。
- **麥克風說明**：語音鈕旁有一行說明聲音由瀏覽器的語音辨識服務處理、可能傳到瀏覽器供應商。原型沒有帳號與後端，暫不放隱私權政策與服務條款頁；開始蒐集個人資料或實際收費前需要補上法務審閱過的版本。
- **載入順序**：滑卡頁只載卡片圖；3D 程式與家具模型等使用者到「我家的條件」才開始下載。第一張卡片圖在 HTML 就預先載入。本機以 Lighthouse（手機模擬）量建置後的首頁：效能 95、無障礙 100、最佳實務 100，LCP 2.7 秒，首頁約 950KB。

## 3D：好看，但不耗資源

- **場景**（`lib/scene.js`）：單椅、茶几、邊櫃、邊几、吊燈、盆栽、花瓶是 Poly Haven 的真實掃描模型，地板、牆面、木皮、布料、皮革是真實材質貼圖，依風格換組合並染成該風格的顏色（CC0，見 `assets/CREDITS.md`）。沙發、收納牆、窗與紗簾仍是程式建的。素材依風格按需載入（每種風格約 2–4MB），載不到時退回全程式建的版本。
- **光**：一張 100KB 的室內 HDRI（CC0）做反射與環境光，陽光從真的窗洞照進來。
- **需求式渲染**：沒有動畫迴圈。相機或設計改變才畫一格；靜止時 GPU 不工作（e2e 會驗證靜止時 frame 數不變）。
- **拖曳時降解析度、直接畫**；停手 240ms 後才補上抗鋸齒與環境光遮蔽（GTAO）。
- **陰影只算一次**；離開畫面就釋放所有資源。Three.js 延後載入，首頁不用付這個成本。
- 不支援 WebGL 的裝置改顯示示意圖。

## 結構

- `lib/`：除了 `scene.js`、`room3d.js` 之外都是純函式，不碰 DOM，各有單元測試。
  - `taste.js`：風格資料與滑卡計分（`applySwipe`、`pickStyle`）。
  - `estimate.js`：依設計估價。`drawings.js`：施工圖。`layout.js`：空間與家具尺寸。
  - `rules.js`：施工前要確認的事（四態）。`render-scheduler.js`：需求式渲染排程。
  - `pins.js`：滑卡的圖與來源。
  - `context.js`：掌握度與區間收窄。`docs.js`：上傳檔案的分類、檢查與摘要。
  - `persist.js`：進度的存檔與還原。
  - `intake.js`：一句話（語音或打字）→ 坪數、長寬高、屋況（`parseHome`）。
  - `art.js`：WebGL 不可用時的示意圖與吉祥物。
- `vendor/`：Three.js r180 與用到的 addon（MIT，見 `vendor/THREE-LICENSE`）。
- `assets/env/apartment.exr`：Poly Haven 的室內 HDRI（CC0），取自 npm 套件 `@pmndrs/assets`。
- `tools/`：`fetch_assets.py` 重新下載並縮小 Poly Haven 素材；`room.html` 是單看 3D 房間的開發頁。不會部署。
- `app.js`：狀態、四個畫面的渲染。

## CI/CD

`.github/workflows/site.yml`：

- **測試**：每個 PR 和每次推到 `main` 都跑單元測試、建置、桌機與手機的端對端測試。
- **自動合併**：從這個 repo 的 `claude/*` 分支開的 PR，測試通過後會自動轉正並合併（合併的是被測過的那個 commit）。想先擋住就在 PR 加上 `hold` 標籤。其他分支與 fork 來的 PR 不會自動合併。
- **部署**：Vercel 的 Git 整合負責，`main` 是正式站，每個 PR 有預覽。

注意：自動合併只在 PR 動到 `prototype/**`、`scripts/build-site.sh`、`vercel.json` 或這個 workflow 時才會觸發（因為測試只在這些路徑變動時跑）；只改文件的 PR 仍需手動合併。
